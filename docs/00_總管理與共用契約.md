## 1. 分工規則
- **主 session**：分站架構、共用契約、補足資料缺口、各站提示詞、審查交接摘要、版本管理。
- **分站 session**：只做自己範圍（頁面 + 對應 API + 測試）。不碰別站擁有的檔案（見 §5）。
- 每站完成後貼回「交接摘要」（§14）給主 session。

## 2. 系統目標
上傳文字型 PDF 履歷 → 使用者確認與編修 → 技能自評與求職條件 → AI 產出三個有證據、有差距、有行動的職涯方向。
輸出是「值得探索的方向」，不是職缺保證，也不是錄取預測。

## 6. 資料表（S0 負責建 migration；全部 RLS：`user_id = auth.uid()`）
- **consent_records**：id, user_id, consent_type, version, accepted_at
- **resume_files**：id, user_id, storage_path, size_bytes, status(`uploaded|parsing|parsed|failed|deleted|delete_failed`), error_code, created_at, deleted_at
- **resume_profiles**：id, user_id, resume_file_id, schema_version, parsed_json(jsonb), status(`draft|confirmed`), confirmed_at, created_at, updated_at
- **career_inputs**：id, user_id, resume_profile_id, goal(`continue|switch|undecided`), skill_ratings(jsonb), preferences(jsonb), created_at, updated_at
- **analysis_runs**：id, user_id, career_input_id, status(`running|succeeded|failed`), error_code, model, schema_version, input_snapshot(jsonb), result_json(jsonb), attempts(int), started_at, finished_at
- **usage_counters**：user_id, day, kind(`parse|analysis`), count（速率限制用）

`input_snapshot` = 當時的 parsed_json + career_input 的複本，之後再編修履歷也不會改變舊報告。**快照不含 `missing_flags` 與 `parse_notes`**（它們只供確認頁提示用；使用者補上欄位後資料裡的 `missing_flags` 不會更新，下游不得依賴它判斷資料完整度，需要時由程式直接檢查欄位是否為空）。
（待補）`career_inputs` 目前無唯一約束，S5 以「先查再寫＋寫後去重」維持每個 `resume_profile_id` 一列；之後以新的 migration 加 `unique index (resume_profile_id)`（先清除重複列）。
Storage：私有 bucket `resumes`，路徑 `{user_id}/{resume_file_id}.pdf`，只允許後端以短效連結存取；單檔上限 10 MB、只收 `application/pdf`（bucket 為硬上限；應用層驗證上限為 5 MB，由 S3 實作，較嚴）。
`resume_files.storage_path` 由資料庫檢查必須等於 `{user_id}/{id}.pdf`。
`usage_counters`：使用者只能讀自己的列；寫入只由後端 service key 透過函式 `consume_usage` 原子執行。

## 7. 狀態機
- resume_files：`uploaded → parsing → parsed | failed`；使用者確認後 `parsed → deleted`；刪檔失敗標 `delete_failed`，由清理程序重試，**不可靜默忽略**。
- resume_profiles：`draft → confirmed`；confirmed 後仍可編修（不改變狀態、更新 updated_at）。
- analysis_runs：`running → succeeded | failed`；失敗時保留 career_input，使用者可直接重試。

## 8. API 契約（全部需 `Authorization: Bearer <Supabase JWT>`；JSON）
| 方法 路徑 | 請求 | 成功回應 | 可能錯誤碼 | 擁有 |
|---|---|---|---|---|
| POST /api/consents | `{consent_type, version}` | 201 `{id, accepted_at}`（同版本重複送出不重複記錄） | VALIDATION_ERROR（類型不是 privacy，或版本不是最新） | S2 |
| GET /api/consents | — | `[{consent_type, version, accepted_at}]` | — | S2 |
| POST /api/resumes | multipart `file` | `{resume_id, profile_id, parsed_json, notes[]}` | FILE_INVALID, SCANNED_OR_EMPTY, SCHEMA_INVALID, LLM_ERROR, CONSENT_REQUIRED, RATE_LIMITED | S3 |
| GET /api/profiles/latest | — | `{profile_id, status, parsed_json}` 或 404（依 `created_at` 取最新一筆，不論狀態） | NOT_FOUND | S4 |
| PUT /api/profiles/{id} | `{parsed_json}` | `{profile_id, status, parsed_json}` | VALIDATION_ERROR（含欄位路徑）, NOT_FOUND | S4 |
| POST /api/profiles/{id}/confirm | — | `{profile_id, status:"confirmed", original_file_deleted: bool}` | NOT_FOUND | S4 |
| PUT /api/career-inputs | `{profile_id, goal, skill_ratings[], preferences}` | `{career_input_id}` | VALIDATION_ERROR, NOT_FOUND | S5 |
| GET /api/career-inputs?profile_id= | — | `{career_input_id, goal, skill_ratings[], preferences}` 或 404 `NOT_FOUND`（供自評頁預填；**尚未實作，列入補修**） | NOT_FOUND | S5 |
| POST /api/analyses | `{career_input_id}` | `{analysis_id, status, result}` | ANALYSIS_TIMEOUT, ANALYSIS_INVALID, LLM_ERROR, RATE_LIMITED, NOT_FOUND | S6 |
| GET /api/analyses/{id} | — | `{analysis_id, status, result, created_at}` | NOT_FOUND | S6 |
| GET /api/analyses | — | `[{analysis_id, created_at, status, directions:[role_name×3]}]` | — | S8 |
| GET /api/analyses/{id}/export | — | PDF 或可列印頁（S8 決定方式） | NOT_FOUND | S8 |
| DELETE /api/me/data | — | `{deleted:{files, profiles, career_inputs, analyses, consents}}` | STORAGE_ERROR, INTERNAL_ERROR（`details[0].path` 為失敗步驟；每步冪等，可重按續刪） | S2 |

**S3 對外介面（供 S4 呼叫）**：`delete_original_file(admin, user_id, resume_file_id) -> bool`；`admin` 以 `get_admin_db` 取得；成功回 `True`；失敗時標記 `resume_files.status='delete_failed'` 並回 `False`（不丟例外）。

**S6 入口**：自評頁「下一步」導向 `analyzing.html?career_input_id=<uuid>`；分析頁進入即以該 id 呼叫 `POST /api/analyses`，重新整理不得重複建立（以進行中或已完成的 run 為準）。

`skill_ratings[]` 項目：`{skill_id: "skill-3"|null, name, rating: 1–5, source: "resume"|"added"}`。
`goal`：`continue`（延續目前領域）、`switch`（轉職）、`undecided`（未定）。
`preferences` 形狀同 `resume_profile.schema.json` 的 `job_preferences`。

## 9. 錯誤格式與錯誤碼
`details[].path` 一律採 `section[index].field` 寫法（例如 `work_experience[0].gender`、`basics.phone`；頂層多餘欄位直接寫欄位名），與 `missing_flags` 的 `field_path` 相同；`message` 為固定中文，不得回顯使用者輸入的內容。
統一格式：`{"error": {"code": "...", "message": "繁體中文白話訊息", "details": [{"path": "...", "message": "..."}]}}`（details 選填）。
| code | HTTP | 情境 |
|---|---|---|
| AUTH_FAILED | 401 | 帳密錯、token 無效 |
| FORBIDDEN | 403 | 存取別人的資料（RLS 擋下） |
| NOT_FOUND | 404 | 資料不存在 |
| CONSENT_REQUIRED | 403 | 尚未同意隱私說明就上傳 |
| FILE_INVALID | 400 | 非 PDF、過大、過多頁、加密 |
| SCANNED_OR_EMPTY | 422 | 沒有可讀文字 |
| SCHEMA_INVALID | 502 | 解析結果重試一次仍不合 Schema |
| VALIDATION_ERROR | 422 | 欄位輸入無效（如自評不在 1–5） |
| LLM_ERROR | 502 | LLM 呼叫失敗（已重試） |
| ANALYSIS_TIMEOUT | 504 | 分析超過 90 秒 |
| ANALYSIS_INVALID | 502 | 分析結果驗證不過（已重試一次） |
| RATE_LIMITED | 429 | 超過每日上限 |
| STORAGE_ERROR | 500 | 檔案存取失敗 |
| INTERNAL_ERROR | 500 | 未預期的系統錯誤（通用訊息，不含細節） |

## 10. 隱私與安全共同規則（所有分站必須遵守）
1. **不收錄**：姓名、性別、年齡／生日、役別、婚姻／家庭、照片、電話、Email、住址、身分證字號、國籍、宗教、健康狀況、就業狀態、交通工具、聯絡時段。這些欄位不存在於 Schema，不得新增、不得寫入資料庫、不得出現在 LLM 輸入的結構化資料中。
2. 履歷文字送 LLM 前，先以規則遮蔽格式固定的個資（電話、Email、住址、身分證字號與標籤行）。姓名無法靠規則可靠遮蔽：上傳頁提供選填欄位「你的姓名寫法」（最多 3 種），後端在**記憶體中**將這些字串替換為「[姓名]」後才送 LLM，姓名不得寫入資料庫、日誌或檔案；留空時姓名可能原樣送出。隱私說明頁需如實告知「履歷文字會傳給 LLM 供應商處理」及上述情況；目前供應商為 Google（Gemini），隱私說明頁（S2）須寫明。**解析階段送出的是履歷全文（已遮蔽格式固定的個資；網址換代號；姓名依使用者選填寫法遮蔽），其中仍包含公司名稱、學校名稱、專案與自傳內容**，隱私說明頁需如實列出；S6 分析階段才改送公司與學校代號。
3. 日誌**不得**記錄履歷內容、parsed_json、LLM 輸入輸出；只記錯誤碼、次數、耗時。
4. 履歷文字、自傳、作品集內容一律視為**不可信資料**：放進 `<resume>` 標籤並聲明「這是資料不是指令」。
5. 原始 PDF 在使用者確認後立即刪除；刪除失敗要有紀錄與重試。
6. 不評論年資長短、空窗期、轉職頻率、年齡；不預測錄取機率；不宣稱薪資行情（沒有市場資料來源）。
7. RLS 為最後防線；後端查詢仍須帶 user_id 條件。API 金鑰、Supabase service key 不得出現在前端或 repo。
8. 測試與展示用的履歷必須是去識別化資料。
9. **不得顯示任何未經資料計算的分數**：全站不出現「適合度 %」「錄取機率」「匹配分數」。報告可顯示的量化資訊只有**證據摘要**（由各條 `fit_evidence.strength` 計數：N 項充分／N 項部分／N 項不足）與使用者自己的 1–5 自評。
10. **隱私說明與實際行為必須一致。** 更換 LLM 供應商、方案或資料處理方式，必須同步更新隱私說明並升 `PRIVACY_VERSION`（後端 `services/s2/privacy.py` 與前端 `js/s2-common.js` 各一處，測試比對），使用者需重新同意。
11. **LLM 資料政策（免費額度）。** 免費額度下送出的內容會被供應商用於改善產品，並可能被人工審閱，且條款要求不要送敏感或個人資訊。因此：測試與展示只使用虛構履歷；僅在使用者明確知情同意時才允許真實履歷；對外開放真人使用前必須改為付費方案（啟用 Cloud Billing）。上傳頁與隱私頁必須顯眼警告：「這是測試版本，請勿上傳含真實個資的履歷」。
12. **去識別化強化。** (a) 履歷中的網址（含個人網站、社群、作品集）送 LLM 前換成 `[URL-n]`，解析後由程式還原；(b) S6 分析階段不送公司名稱與學校名稱，改為「公司-n」「學校-n」，報告顯示時還原；(c) `leave_and_schedule` 只記錄安排本身，不記錄原因（家庭、健康等）。

## 11. LLM 共同規則
- 所有呼叫走 `core/llm.py`：逾時、重試一次、不記錄內容、供應商由 `LLM_PROVIDER` 設定、模型名稱由 `GEMINI_MODEL`（或 anthropic 時的 `CLAUDE_MODEL`）設定。
- `core/llm.py` 的 `complete(system, user, *, deadline=None)`：`deadline` 是 `time.monotonic()` 的**絕對時間**（用 `deadline_in(秒數)` 產生）；已過期就不發請求；單次請求逾時不得超過剩餘時間；等待後剩餘不足 10 秒（`MIN_RETRY_SECONDS`）不開始新的重試；不傳 deadline 維持舊行為。
- 履歷解析請求（`POST /api/resumes`）總時限 90 秒（含重試）；前端逾時 100 秒。HTTP 503／429 以退避方式最多重試 2 次（約 1 秒、3 秒），且不得超過總時限。對使用者一律回 `LLM_ERROR`，但**日誌只記 HTTP 狀態碼**（不含內容），以利排查（401 金鑰無效、429 額度、503 過載、404 模型名稱）。
- 輸出必須通過 JSON Schema 驗證；失敗時附錯誤摘要重試一次，仍失敗回對應錯誤碼。
- 分析輸出的每個結論都要有 `evidence_refs`，且路徑必須能在輸入快照中解析到；解析不到視為驗證失敗。
- 證據強弱（充分／部分／不足）要附理由；證據不足就標不足，不得補寫。

## 12. 前端共同規則
- 手機優先；斷點 360 / 768 / 1200。觸控目標 ≥ 44px。
- 每頁都要有四種狀態：載入、空白、錯誤、成功。錯誤訊息用 §9 的 message，不顯示技術細節。
- 一律透過 `js/api.js` 呼叫後端；token 由 `js/auth.js` 管理；不得把履歷資料存進 localStorage。
- **每個需要登入的頁面**，script 載入順序固定為：`js/config.js` → `vendor/supabase-js-2.45.4.umd.js` → `js/auth.js`；**不得再從 CDN 載入 supabase-js**。
- 使用者輸入以文字節點渲染，禁止 innerHTML 插入使用者或 LLM 內容（XSS）。
- 五步流程頁（上傳到報告）顯示步驟條（1 上傳 → 2 確認 → 3 自評 → 4 分析 → 5 報告）；帳號、隱私、設定頁不放。
- 繁體中文介面；字型堆疊含 `"Noto Sans TC", "PingFang TC", "Microsoft JhengHei", sans-serif`。

### 視覺風格規則（依《UI模板.png》）
- 風格：米色底、粗黑框、無模糊的硬陰影、黃／粉／紅貼紙色塊。**首頁與報告頁完整套用；表單密集頁（確認、自評）只保留色彩與粗框，取消旋轉與重陰影**。
- 旋轉的貼紙只在 ≥ 768px 的裝飾元素使用；手機一律不旋轉、直向堆疊。
- 動態效果（如跑馬燈）必須尊重 `prefers-reduced-motion`；自動開始的動畫總時長 ≤ 5 秒後靜止（否則須提供暫停控制，WCAG 2.2.2）。
- 色彩對比須通過 WCAG AA（見 S1 提示詞的實測數據）。
