## 2. 與契約／提示詞的差異
- **跑馬燈保留，但隱藏暫停按鈕**：提示詞寫「不實作跑馬燈」，但 S1 交接摘要記載 2026-11-11 已明確要求，且首頁視覺預覽含跑馬燈，所以保留。使用者要求拿掉暫停按鈕，已用 `s2-pages.css` 的 `.marquee__pause{display:none}` 隱藏（滑鼠移上仍暫停、減少動態時仍為靜態）。這會讓頁面沒有可操作的暫停控制，屬無障礙上的取捨，請主 session 知悉。要拿掉整個跑馬燈就刪 `index.html` 的 `.marquee` 區塊。
- 首頁骨架取自你確認過的 `index-preview.html`；其頁面專用 CSS 放新檔 `css/s2-pages.css`（沒有改 S1 的三份 CSS）。示意卡改為「證據：N 項充分／部分／不足」，沒有百分比。
- 步驟條：帳號／隱私／設定頁不在五步流程內，沒有放步驟條（§12 寫「所有頁面」，請確認是否照字面要求）。
- 「先看範例報告」為停用按鈕，S7 完成後改成連結（HTML 內有註解）。
- 隱私頁寫明：登入用的 Email 存在登入服務、不進履歷資料；姓名無法可靠遮蔽，可能原樣送出；供應商端的處理我們無法替你刪除。最後一點是我加的誠實說明。
- 隱私頁有一句「更換供應商時會更新說明並請重新同意」，這是產品承諾，請確認。
- 同意版本號 `PRIVACY_VERSION = "2026-11-12"`：後端 `privacy.py` 與前端 `s2-common.js` 各一份，測試會比對。改隱私說明時兩處一起升版，所有人就必須重新同意。
- `POST /api/consents`：版本不是最新、類型不是 `privacy` 都回 `VALIDATION_ERROR`；同版本重複送出不會重複記錄。
- `DELETE /api/me/data`：先刪 Storage（含資料夾內的孤兒檔，且只刪自己資料夾底下的路徑），再依 analysis_runs → career_inputs → resume_profiles → resume_files → usage_counters → consent_records 刪除，最後逐表與 bucket 驗證為 0 筆。任一步失敗中止並回 `STORAGE_ERROR`／`INTERNAL_ERROR`（`details[0].path` 是失敗的步驟）；每步冪等，重按即可接著刪完。

## 4. 未完成或已知問題
- **S0 介面已對照 `core/db.py` 與 S0 交接摘要**：`CoreStore`（`services/s2/compat.py`）用真實的 `Db.select/select_one/insert`、`AdminDb.select/delete`，以及上述補丁的兩個方法；`tests/s2/test_core_store.py` 用假 HTTP 對真實 `Db`／`AdminDb` 驗證請求（每個查詢都帶 user_id、儲存空間的列出與刪除都限定在自己的 user_id 前綴）。
- **需要先套用 S0 補丁**：`s0-patch/db_admin_user_files.patch` 在 `AdminDb` 新增 `list_user_files(user_id)`（列出 `{user_id}/` 底下全部物件）與 `delete_user_files(user_id)`（批次刪除，含資料表沒有紀錄的孤兒檔）。S2 的刪除與驗證都用它，所以 bucket 也會驗證為 0 筆。這是動 S0 擁有的檔案，列入契約外的共用檔案變更，請你決定由誰套用（`git apply s0-patch/db_admin_user_files.patch`）。
- `AdminDb`／`Db` 會對非 UUID 的 user_id 丟 `ValueError`；S2 的 `_fail` 會把它轉成 `INTERNAL_ERROR`，正常情況（Supabase 的 user_id 皆為 UUID）不會發生。
- 前端已對照 `api.js`：用 `Api.get`、`Api.post`、`Api.del`。`auth.js` 也是依 S1 摘要中唯一已知的 `Auth.logout()` 與「token 由 auth.js 管理」推測介面；`Auth.getToken()` 是同步的，頁面需先 `await Auth.ready`。
- 目前沒有已知的未解問題；Supabase 的 Email 驗證仍為關閉（待決策 #6，S9 前決定）。
- Supabase 專案的密碼最小長度要設成 8，才會和前端規則一致；Email 驗證目前依待決策 #6 假設為關閉（開啟時註冊頁會顯示「請到信箱確認」）。
- supabase-js 從 CDN 載入並固定 2.45.4。

## 5. 需要主 session 決策
上述 3 的契約變更、無暫停控制的跑馬燈、步驟條、供應商更換的重新同意承諾；另外：S3 的姓名遮蔽方式（規則無法可靠辨識姓名，選項：僅遮有標籤的行／讓使用者輸入姓名後在記憶體中替換／送出前讓使用者預覽並刪除），這會牽動契約 §10.1，決定後隱私說明頁與 `PRIVACY_VERSION` 需同步更新。

## 實測結果（2026-11-12，使用者於本機＋真實 Supabase 執行）
- 註冊 → 隱私同意 → 登出 → 登入 → 登出完整可走；錯誤路徑（登入失敗、重複註冊、密碼規則、未勾選同意）皆有白話提示。
- 登入後已同意者直接進入下一頁；未登入開 settings.html 會導回登入頁。
- 「刪除我的資料」：刪除後以 Supabase 直接查詢，該 user_id 在各表與 bucket 皆為 0 筆（含故意放入的孤兒檔）；帳號保留，重新登入後需重新同意。
- 手機 360px：五頁皆可完整操作、無橫向捲動（修正過一次：頁首登入按鈕在手機被 S1 的 `.site-nav` 收起，已改用 `.account-nav`）。
- Supabase 設定：Confirm email 關閉、密碼最小長度 8。
- 單元測試 21 項在真實 repo 全過。

## auth.js 介面
`Auth.ready`（Promise）、`isConfigured()`、`getToken()`、`isLoggedIn()`、`getEmail()`、`login(email, pw)`、`register(email, pw)`（回 `{ok, needsConfirm}`；重複註冊丟 `EMAIL_EXISTS`）、`logout({redirect})`（預設導向 login.html）、`requireLogin()`（未登入導向 `login.html?next=…`）、`checkPassword(pw)`、`friendlyError(err)`。

## require_consent 用法
```python
from app.services.s2.privacy import require_consent, consent_required

@router.post("/api/resumes")
def upload(user_id: str = Depends(consent_required)): ...   # 方式一：依賴，回傳 user_id
# 方式二：require_consent(user_id, store)，store 用 Depends(get_store)（from app.services.s2.compat）
# 與 rate_limit 並用時，若要「先檢查同意再扣額度」，請用方式二，再呼叫 rate_limiter.consume
# 未同意最新版丟 CONSENT_REQUIRED（403）
```
