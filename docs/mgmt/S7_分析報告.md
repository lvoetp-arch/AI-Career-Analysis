# 分站 S7：分析報告頁（最終展示重點）

## 工作環境與提交規則（本站必須遵守）
- 工作目錄為專案根目錄（`AI Career Analysis`，遠端 repo：`lvoetp3-cpu/AI-Career-Analysis`，私有）。環境為 Windows：指令請用 Windows 可執行的寫法（`python -m pytest`、`.venv\Scripts\activate`），不要寫 Linux 專用指令。
- 分支：從最新的 `main` 開出 `s7-report`，只在此分支提交；不得直接提交到 `main`，不得 force push。
- 只修改本站擁有的檔案（契約 §5）。需要動共用檔案時，不要自行改，寫進交接摘要。
- **絕對不可提交**：`.env`、任何金鑰（Supabase service key、Anthropic 金鑰）、真實履歷、`test-resumes/`、含個資的截圖或日誌。每次 commit 前先看 `git status` 與 `git diff --staged`。
- commit 訊息用繁體中文或英文皆可，一個 commit 做一件事；最後一個 commit 前，本站測試必須全部通過。
- 完成後把交接摘要（契約 §14 格式）存成 `docs/handoff/S7.md` 並提交；摘要中不得含個資或金鑰。你不需要自己合併分支，使用者審查後才合併。

## 你的角色
你負責使用者最終看到的報告頁。這是期末展示的重點，視覺與可讀性要花最多心思。共用規則以《00_總管理與共用契約.md》為準。上游未完成時，請用 `analysis_result.schema.json` 做出一份**符合 Schema 的假結果**開發。

## 做
`frontend/report.html?id=<analysis_id>`（資料來自 `GET /api/analyses/{id}`）：
1. 頁首：一則固定聲明橫幅——「這是依您提供的資料產生的方向探索建議，不是職缺保證，也不是錄取預測」。
2. 三個方向的總覽：排名、方向名稱、一句摘要、**證據摘要條**（由該方向所有 `fit_evidence.strength` 計數：N 項充分／N 項部分／N 項不足，以黑框進度條呈現各占比；**不得顯示適合度百分比或任何未經資料計算的分數**）、與求職條件的吻合度（雇用型態／工作模式／薪資／時間安排四個標籤：吻合／部分／不吻合／未知，文字 + 圖示，不只靠顏色）。
3. 每個方向的詳細內容：
   - 為什麼適合：每條 claim 配「證據強弱標籤」與理由；點開可看對應的履歷或自評來源（依 `evidence_refs` 顯示可讀的來源名稱，如「工作經歷：合昇昌國際」，不要顯示原始 JSON 路徑）
   - 差距：技能、你的自評分數（沒評顯示「未自評」）、為何重要、優先度
   - 風險與不確定性
   - 30／60／90 天行動：三欄時間軸（手機改為垂直），每項行動附「可檢驗的產出」
4. `data_gaps` 以「想讓分析更準，可以補充…」區塊顯示，並提供返回修改的連結。
5. 版面：手機為三個方向的手風琴；桌面為頁籤 + 單一方向詳細內容。
6. 預留「歷史」與「匯出」入口按鈕（S8 完成前以停用狀態顯示，標示「即將提供」）。
7. 狀態：載入、不存在（NOT_FOUND）、分析失敗的結果（引導回重試）、成功。
8. **範例報告頁** `frontend/sample_report.html`：用你製作的假資料（`frontend/sample/analysis_sample.json`，必須通過 Schema，內容為虛構人物、不含任何真實個資）渲染同一套報告版型，頁首固定標示「範例」。首頁的「先看範例報告」按鈕連到此頁，不需登入。
9. **首頁「用範例履歷試試」入口**（契約 v0.4）：提供虛構履歷（`test-resumes` 內 R1 的解析結果 fixture）一鍵載入完整流程，免上傳；與「先看範例報告」並列；頁面標示「範例資料，非真人」。這是對 S2 首頁檔案的共用檔案變更，列入交接摘要，由使用者決定怎麼套用。
10. 行動區塊以「30 天內先做」為主，90 天內為後續；視覺可參考模板的勾選清單，但**勾選狀態不儲存**（Schema 沒有此欄位），只作為靜態清單。
11. 所有文字以文字節點渲染；LLM 產出內容不得以 innerHTML 插入。

## 前端載入規則（契約 §12）
每個需要登入的頁面，script 順序固定為 `js/config.js` → `vendor/supabase-js-2.45.4.umd.js` → `js/auth.js`；不得從 CDN 載入 supabase-js。

## 不做
分析本身、歷史清單、匯出功能實作。

## 驗收標準
- 用「三個方向各種組合的假資料」測試：證據為空陣列、差距為空、risks 為空、data_gaps 有／無、薪資 unknown，版面都正常。
- 360 / 768 / 1200 寬度無破版；列印預覽可讀（為 S8 預留）。
- 所有「不足」證據都有明顯標示，不被視覺淡化。
- 對照 Schema 逐欄確認每個欄位都有顯示位置。
- 全站（含範例頁）搜尋「%」「錄取」「機率」，不得出現適合度分數；證據摘要的數量加總需與 `fit_evidence` 筆數一致（測試）。
