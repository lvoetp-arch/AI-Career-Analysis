## 做
**API**（`routers/profiles.py`）：
- `GET /api/profiles/latest`、`PUT /api/profiles/{id}`：送入的 `parsed_json` 必須通過 Schema 驗證；**含有 Schema 沒有的欄位（如 phone、gender）一律拒絕**，回 `VALIDATION_ERROR` 並指出欄位路徑。更新 `updated_at`。
- `POST /api/profiles/{id}/confirm`：狀態改 `confirmed`、寫 `confirmed_at`，**並呼叫 S3 提供的 `delete_original_file`**；回傳 `original_file_deleted`。刪檔失敗時仍完成確認，但必須回 `false` 並讓檔案狀態為 `delete_failed`，前端要顯示「原始檔刪除中，稍後會自動處理」。

**頁面** `frontend/review.html`（手機優先）：
- 頂部說明：「請確認系統讀到的內容是否正確；沒寫的欄位不會被推測」。
- 區塊（可收合；手機一次展開一個）：求職條件（預填自履歷、可修改）、工作經歷、學歷、專長（依履歷分組）、專案、作品集與連結、證照與語言、自傳（顯示原文，可編修）。
- 每個項目可編輯、刪除、新增；日期欄位限制 YYYY-MM 或 YYYY；網址欄位驗證格式。
- `missing_flags` 以警示標籤顯示在對應欄位旁（例如「作品集網址被截斷」「未寫休假方式」），點擊捲動到該欄位。只提示，不強迫補。
- 「儲存草稿」與「確認並繼續」兩個按鈕；確認前有一句提示：「確認後會刪除您上傳的原始 PDF，之後分析只使用這裡的內容」。
- 離開頁面前若有未儲存變更要提醒。
- 四種狀態齊全；表單錯誤逐欄顯示後端回傳的路徑訊息。

## S3 審查後的補充（契約 v0.5）
1. **呼叫 S3 的刪檔函式**：`delete_original_file(admin, user_id, resume_file_id) -> bool`；`admin` 用 `get_admin_db` 取得；失敗不丟例外，回 `False`，函式已把檔案標為 `delete_failed`。`confirm` 回傳的 `original_file_deleted` 就是這個結果。
2. **你暫時擁有 `frontend/js/upload.js` 的兩處修改權**：(a) 檔頂的 `REDIRECT_TO_REVIEW` 改為 `true`（review.html 完成後）；(b) 上傳逾時後，錯誤訊息旁加「檢查結果」按鈕：呼叫 `GET /api/profiles/latest`，有 draft 就導向 `review.html`，沒有就顯示「尚未產生結果，請重新上傳」。其他部分不得改動。(c) 你另外擁有 `frontend/upload.html` 的**一處**修改權：把 supabase-js 從 CDN 改為 `vendor/supabase-js-2.45.4.umd.js`（順序 `config.js` → vendor → `auth.js`，見契約 §12）。你自己的 `review.html` 也照此載入。
3. **空欄位提示（由前端用 `parsed_json` 計算，不靠 LLM 的 `missing_flags`）**：下列欄位為 null 或空時，在對應位置顯示柔性提示「履歷沒寫這項，可以在這裡補充（不補也可以）」：希望職稱、希望待遇、遠端意願、休假與工時、希望地點、專長（整個區塊空）、工作經歷與專案（兩者皆空）。這些提示只提醒，不阻擋「確認並繼續」，措辭不得暗示使用者資歷不足。
4. 自傳、專案描述等自由文字可能含注入內容（見虛構履歷 R6）：一律以文字節點顯示，不可用 innerHTML。
5. `leave_and_schedule` 只顯示與編修「安排」本身；不新增「原因」欄位。
