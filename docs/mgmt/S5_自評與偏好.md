## 做
**API** `PUT /api/career-inputs`（契約 §8）：
- 驗證：`goal` 三選一；`skill_ratings` 每項 `rating` 為 1–5 的整數；`name` 非空、長度上限；新增技能（source=`added`）最多 10 項；總技能數上限 30；`profile_id` 必須屬於本人且已 `confirmed`（否則 `VALIDATION_ERROR` 或 `NOT_FOUND`）。
- 一個 profile 對應一份 career_input，重複送出為更新。`preferences` 以 `job_preferences` 的 Schema 驗證。

**頁面** `frontend/assess.html`：
- 職涯目標：三個大選項（延續目前領域／轉職／尚未決定）。
- 技能自評列表：預設列出已確認履歷中的技能（依履歷分組），每列 1–5 大按鈕；顯示各級定義（點開說明）。每項必須評分，或按「不評」移除（移除的技能不進入差距分析）。
- 「加入其他技能」：使用者可補上履歷沒寫、但想評估的技能（上限 10）。
- 求職偏好確認：預填雇用型態、工作地點、遠端意願、上班時段、待遇、可上班日、休假與工時等；全部可改、可留空。待遇欄位只存使用者填的原文或區間，不補市場資料。
- 驗證失敗時逐項標示；「下一步」進入分析頁。四種狀態齊全。

## 待主 session 決策（遇到請寫進交接摘要，不要自行定案）
- 若履歷技能少於 3 項，是否要求至少加入 3 項？（預設：不強制，但提示「資料越少，分析越保守」）

## 前端載入規則（契約 §12）
每個需要登入的頁面，script 順序固定為 `js/config.js` → `vendor/supabase-js-2.45.4.umd.js` → `js/auth.js`；不得從 CDN 載入 supabase-js。

## S4 審查後的補充（契約 v0.7）
1. 已確認的履歷從 S4 的 `GET /api/profiles/latest` 取得；技能清單來自 `parsed_json.skills`（依 `group` 分組）。
2. **不得使用 `missing_flags` 判斷資料完整度**（使用者補欄位後它不會更新）；需要時直接檢查欄位是否為空。不顯示、不使用 `skills[].years_text`。
3. 驗證失敗的 `details[].path` 沿用 `section[index].field` 寫法（契約 §9），`message` 不回顯使用者輸入。
4. 你暫時擁有 `frontend/js/review.js` 檔頭 `NEXT_PAGE` 常數的修改權（確認頁的下一步目前指向 `assess.html`，請確認路徑與你的頁面一致，其他部分不得改動）。
5. **自評不是已證實能力**：頁面與資料都要把「自評級別」與履歷證據分開呈現，不得把自評直接標成已驗證能力（Word 執行書規定）。

## 不做
履歷編修、分析、報告。

## 驗收標準
- 評分 0、6、小數、字串都被拒絕並回 `VALIDATION_ERROR`（對應 Word 測試中的輸入無效情境）。
- 未確認的 profile 不能建立 career_input。
- 手機上評分按鈕可單手點擊，30 項技能的列表捲動順暢。
- 頁面上的等級說明與 Word 文件定義一致（逐級對照）。
